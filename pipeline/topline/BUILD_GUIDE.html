Overview: the closed loop

Seven layers. Information flows down from canonical through generators into runtime and analytics. Analytics feeds the client dashboard for ongoing access. Approved study results promote into norms via a QC gate; norms feed back into canonical (priors for next study) and forward into the simulator. One loop, one source of truth.

L1 — Canonical layer (the source of truth)

Partial

Three classes of canonical content. Shared libraries are stable across studies (segments, scales, the typing tool spec). Versioned registries change deliberately with explicit version stamps (battery templates, ROI model coefficients, DQMA parameters). Per-study definitions select from libraries, override where the study deviates, and define this study's new content — including composites, which are study-specific.

Correction from v0.1 — composites are per-study, not canonical. Each study defines its own indices (MBS, SDS, EDS, SCS, CFS, PFS, SCF, HKS for HIV; entirely different composites for the next study). The architecture must support this directly: composites live in per-study YAML, with formulas referencing this study's items. A recurring composite (e.g., BCS, which appears in many studies) can be promoted into a Composite Library through the QC gate later — but the v1 architecture assumes everything composite is study-local.

What's canonical vs. what's per-study

  • Canonical: the 16 segments, the typing tool design, the QBALLOT/QPARTY routing matrix, the ROI model coefficients (versioned), the DQMA parameter set, scale definitions, the Item Bank with stable IDs.
  • Per-study (overrides + new content): this study's screeners, eligibility rules, sample frame, message stimuli, persona variants, and all composite formulas.
  • Battery Templates are structural, not content. "HIVSTIGMA-style" means "a Likert-7 agree battery with split-sample fielding"; the actual items belong to the per-study definition (referencing item_bank IDs where reused, or introducing new ones).

L2 — Authoring layer

To build

Analysts edit in Excel. A sync script converts to canonical YAML. YAML is versioned in git. The analyst never sees YAML until a future Study Editor UI replaces Excel. Excel is the v1 authoring interface because it carries no migration cost and matches existing workflow.

Why the two-step (Excel → YAML → git)

  • Excel diffs are unreadable. An .xlsx file is a zip of XML. Git stores it but cannot show what changed between v1.0 and v1.1. YAML diffs line-by-line.
  • Excel format drifts. A YAML schema survives Excel column reshuffling. The YAML is the contract; Excel is one writer.
  • Future writers besides Excel. A Study Editor UI eventually writes YAML directly. Excel is the v1 interface, not the long-term one.
  • Validation between Excel and YAML. Type likert7_agreement instead of likert7_agree and the sync rejects it with a row-and-column error before any generator sees malformed input.

To build

L4 — Field / runtime layer (the live survey)

In development

What runs during fieldwork. Decipher hosts the typing tool, pre-routing logic, eligibility check, and DQMA router as stages in the respondent flow. The DQMA reads its own live state from Supabase, makes routing decisions per respondent, and rebalances quotas every 6 hours or every 50 completes. ROI scoring fires at completion.

Critical separations

  • DQMA parameters vs. dqma_state. Parameters (kappa thresholds, tier budgets, ROI weights, rebalance cadence) are canonical Layer 1, set by the analyst, change only on deliberate methodology updates. dqma_state is operational live state, changes every 6 hours, lives in Supabase as row-per-segment.
  • Typing Tool is Layer 1 platform code, identical across studies. The 13-item GOP set, 15-item DEM set, BIBD design, centroid matrices, and Z-score parameters are baked in. No per-study override.
  • Pre-routing + eligibility lives inside the typing tool stage. Fires before the DQMA call. DQMA receives an already-eligible respondent with a segment probability vector; its job is routing-by-quota, not eligibility.
  • Norms are read-only during fieldwork. DQMA borrows from prism_norms.db for Bayesian shrinkage of ROI priors. Writes to norms happen only via the QC gate (L6).

Exists (HIV prototype + dashboard scaffold)

The data feed chain

  • dashboard.json is the single data feed. One artifact, three consumers. Topline HTML embeds it. Banner books read from it. Client dashboard imports it (as the auto-generated studyData module already shown in AudienceROI.jsx and MessageMap.jsx).
  • Client dashboard accumulates studies. Each completed study contributes its dashboard.json as a new entry in studyData. The dashboard already keys by study (ESI, MA in the current scaffold); HIV is the next addition. Over time the dashboard becomes the persistent multi-study window for clients.
  • Canonical feeds in three places. compute_core registries (from L3 topline generator), SPSS labels (from L3 SPSS generator), and dashboard schema for module layouts (from L3 dashboard schema generator). Same canonical, three downstream views, no drift.

L6 — Norms accumulation

In development

Each completed study is a candidate for promotion into the longitudinal normative database. The QC gate is explicit: an analyst reviews data quality, item-by-item, then publishes the relevant normative records into prism_norms.db. This is the loop that gives later studies stronger priors and eventually feeds the simulation engine.

Why explicit QC rather than auto-publish

  • Auto-publish will eventually poison the priors. Some waves contain known data quality issues (vendor anomaly, copy error in stimuli, screener mis-routing); those waves sit in analytics but do not promote into norms.
  • The gate doesn't have to be slow. The five checks above can be a one-screen checklist with auto-computed flags ("3 items below prior distribution by > 2 SD — review?"). The analyst confirms or excludes; publishing is a single button.
  • The gate is also where Item Bank backfill happens. The first time HIVSTIGMA_SB_1 is fielded, it becomes an item_bank entry on publish. Future studies referencing the same item inherit its prior distributions.
  • Composite promotion is selective. Most composites stay study-local. Only recurring composites with stable definitions (BCS is the obvious candidate) get promoted into the Composite Library on publish. The promotion criterion: the composite has the identical formula across at least 3 studies.
§ 7

L7 — Simulation engine (the endpoint)

Future

The eventual replacement for the topline + dashboard as a primary deliverable. Reads from the canonical (message frame structure, segment definitions, ROI model) and from prism_norms.db (baseline distributions). Lets a user ask: "what happens to coalition support among CEC + TC if ALIGN_MOVE on message X increases by +0.5?" Useful only when enough longitudinal data has accumulated — probably 8–12 published studies.

Sequencing dependency

  • The simulator is the end-state because every other layer feeds it. Building it before the canonical and norms are settled is the classic "build the cool UI first, regret the data model later" anti-pattern.
  • Norms need at least 6–8 studies of stable canonical structure before scenario projections have meaningful uncertainty ranges.
  • The simulator is also the point at which RCG's competitive position becomes hardest to replicate. Audience platforms can be cloned; a 50-study longitudinal normative database with stable item identifiers and a fitted ROI model cannot.
  • The simulator integrates into the client dashboard, not as a separate app. Same Vercel project, new route. Clients move from "view our segments" to "view what happens if we move them" without changing tools.

Prototyping plan: HIV as the proof study

Use the just-fielded HIV study as the proof case. Everything about it (data, items, composites, segments, dashboard) is already known and validated. The prototype's job is to demonstrate that the canonical-driven architecture reproduces the existing artifacts bit-identically — same numbers, same labels, same dashboard. Once that round-trip works, every future study runs through canonical from day one.

Ship the 48-hour client dashboard with HIV data

Before any canonical work begins: export dashboard.json from the current HIV compute_core build. Add a HIV entry to the client dashboard's studyData module alongside the existing ESI and MA entries. Wire it into the navigation. Deploy to Vercel. Verify all five components (SegmentMap, IdeologyHeatmap, AudienceROI, SegmentProfile, MessageMap) render correctly for the HIV study.

Hand-write the canonical YAML for HIV

Cover: study metadata, library selections (which battery templates, which scales, which ROI model version), all items with stable item_ids, all eight composites with formulas (MBS, SDS, EDS, SCS, CFS, PFS, SCF, HKS), module layout, demographics, MaxDiff stimuli (when MaxDiff activates in V2), the trap item flag for K5. If any piece of the current HIV dashboard doesn't fit cleanly into the schema, the schema needs another field. Iterate until it fits.

The output is line-by-line verifiable: open 260433.sav in SPSS, look at the variable labels and value labels already there, diff them against what the generator produces. If they match exactly, the schema is right. If they don't, find the mismatch, fix the schema, regenerate.

5

Build the Excel authoring workbook

Reverse-engineer Excel sheets from the proven YAML schema. One sheet per top-level YAML section (Study, Segments, Scales, Batteries, Items, Composites, Modules, MaxDiff Stimuli, Demographics). Data validation: scale_id is a dropdown sourced from the Scales sheet; battery_id from Batteries; composite_targets is a multi-select from Composites. Write the sync script that reads the workbook and emits the same YAML you hand-wrote in step 1. Round-trip the HIV YAML through it: open in Excel, save, sync, diff against original.

Deliverable: prism_study.xlsx template + sync_to_yaml.py Acceptance: round-trip from YAML → Excel → YAML produces identical YAML Effort: 1-2 weeks
6

Author the next study from canonical (day one)

Next study after HIV: the analyst opens the Excel template, edits in study metadata, picks library elements, defines new composites, runs sync, gets next_study.yaml. Runs the SPSS generator — gets the labels file for fielding. Runs the topline generator — gets the registries for compute_core. Runs compute_core.py after field — gets the dashboard. Zero hand-typing into Decipher labels, SPSS labels, or topline registries. This is the moment the new architecture replaces the old workflow for real.

Deliverable: first study fielded canonical-first Acceptance: analyst confirms no hand-edited config files outside the YAML Effort: integrated into next study timeline
7

Decipher XML generator and DQMA runtime generator (parallel)

Once two studies have round-tripped through canonical, build out the remaining generators. Decipher XML generator works with Forsta as a partner — Forsta provides the configuration tools you'll ultimately drive from canonical. DQMA runtime generator emits the study registry insert (eligibility rules, ROI weights, n_base targets) that the live DQMA reads. After this step, the canonical YAML feeds both the survey instrument and the field management system, closing the loop completely.

Deliverable: generate_decipher_xml.py + generate_dqma_runtime.py Acceptance: full study can be configured, fielded, managed, and reported from one YAML Effort: 3-4 weeks
8

QC gate + Item Bank backfill (parallel track)

With three or four canonical studies in production, build the QC gate as a one-screen checklist that reads dashboard.json for each completed study, runs the five health checks, and writes approved records into prism_norms.db. The first backfill is item-level: every fielded item with an assigned item_id becomes an entry in the Item Bank with its observed distributions across the four (or more) studies. From here, future studies inherit Item Bank priors automatically.

Deliverable: QC gate UI + populated Item Bank Acceptance: next study's DQMA reads improved priors from accumulated norms Effort: 3-4 weeks

What this plan does and doesn't commit to

  • Commits to: proving the canonical schema against an existing, validated study (HIV) before generalizing; shipping the 48-hour client dashboard with HIV today using the existing pipeline; the round-trip test as the gating criterion for moving forward; sequential, validated, low-risk progression from hand-written YAML to fully generated artifacts.
  • Doesn't commit to: a Study Editor UI before the YAML schema is proven across 3-4 studies; the simulation engine before norms are accumulated; activation pipelines (LiveRamp, DSPs) — out of scope per your direction; migrating off Decipher — Forsta partnership path is preferred.
  • Risk surface: the round-trip test (step 4) is where the schema is proven or broken. If the diff shows fundamental mismatches that can't be patched by adding YAML fields, the schema needs structural revision before steps 5–8 proceed. Budget for one iteration of schema redesign between steps 3 and 4.
